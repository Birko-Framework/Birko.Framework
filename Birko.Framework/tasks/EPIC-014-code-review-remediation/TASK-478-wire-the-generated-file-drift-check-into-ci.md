# Decide whether the generated-file drift check belongs in CI

## Context

[[TASK-477]] found that `PgColdTableProbeModels.g.cs` carried a `// GENERATED by … do not hand-edit`
header while nothing could regenerate it — a hand-maintained file wearing a generated file's warning.
The port added `--check`, which regenerates to memory and exits 1 naming any file that has drifted:

```bash
dotnet run tools/gen-cold-table-probes.cs -- --check
```

Nothing runs it. The defect it detects is exactly the one that was just found, and it went unnoticed
for as long as both files existed — so the question is whether a CI step is worth the cost.

## The decision to make

Add a step to `.github/workflows/build-and-test.yml` running `--check` after the solution build, or
leave it as a manual pre-release check.

- **For:** it is fast (no restore, no test run), it fails loudly, and the defect it catches is proven
  to survive indefinitely without it.
- **Against:** it is one more thing that can redden a PR for a reason unrelated to the PR, and
  TASK-476 deliberately drew the same boundary around `--fail-on-finding` rather than wiring the
  audits into CI by default. Consistency argues for deciding both together.

⚠ **Decide it with `--fail-on-finding`, not separately.** Two tools with the same shape landing on
opposite sides of "does this run in CI" is the kind of split nobody can explain later.

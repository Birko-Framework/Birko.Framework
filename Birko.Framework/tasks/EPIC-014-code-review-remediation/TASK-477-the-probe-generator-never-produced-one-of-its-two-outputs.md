# The cold-table probe generator did not run on Linux, and never produced one of its two outputs

## Context

Found immediately after [[TASK-476]] closed, by the question *"are the .ps1 files deleted?"* — the
answer was yes for the four at the aggregator root, and **no for the repo**. TASK-476's survey was run
from `Birko.Framework/` (the aggregator); `tests/` is a *sibling* at the repo root, so it was never in
the search path. A whole-repo sweep found a fifth script:
`tests/Birko.Data.SQL.SqLite.Tests/tools/gen-cold-table-probes.ps1`.

⚠ **The lesson is the scope of the search, not the script.** A sweep rooted where you happen to be
standing answers a narrower question than the one asked, and reports the narrow answer in the wide
question's words. Same family as [[TASK-474]]: *a guard for "none" is not a guard for "fewer than
asked for."*

## The two defects

**1. It did not run on Linux, and said it had.**

```powershell
$out = Join-Path $PSScriptRoot '..\ColdTableProbeModels.g.cs'
[System.IO.File]::WriteAllText((Resolve-Path -LiteralPath (Split-Path $out) | ...))
```

On Linux the backslash is an ordinary filename character, so `Split-Path -Leaf` returns the literal
string `..\ColdTableProbeModels.g.cs`. The script writes **a junk file with a backslash in its name
inside `tools/`**, leaves the real generated file untouched, prints `wrote 200 probe types` and exits
**0**. Reporting success having done nothing — the same family as the four audits in TASK-476.

**2. ⚠ It never produced `PgColdTableProbeModels.g.cs`, which claimed it did.**

That file carried `// GENERATED by tools/gen-cold-table-probes.ps1 — do not hand-edit`, while
`Birko.Data.SQL.PostgreSQL.Tests` **has no `tools/` directory**, and the committed script hardcoded
the SQLite count (200), prefix (`Probe`), width (3), namespace, class name (`ColdTableProbes`) and
output path. It could not have emitted a 60-type `PgProbe00` file in another namespace. So one of the
two "generated" files was a **hand-maintained copy wearing a generated file's warning not to
hand-edit it** — the worst of both: nobody dared edit it, and nothing could regenerate it.

The generator existed precisely so these would be derived artefacts *"rather than 200 hand-written
lines nobody dares touch"*. For half its output that was untrue from the start.

## What changed

`Birko.Framework/tools/gen-cold-table-probes.cs`, a .NET 10 file-based app, per the rule TASK-476
recorded in `CLAUDE-maintenance.md`. It carries **both targets as explicit profiles**, so both files
are now genuinely generated and both provenance headers are true.

- **⚠ It cannot live beside the suite it feeds, and that is not a preference.** The `.ps1` sat in
  `tests/Birko.Data.SQL.SqLite.Tests/tools/`, which is fine for a file the compiler ignores. A `.cs`
  file there is swept up by that project's default `**/*.cs` glob and compiled into the test assembly,
  where its top-level statements are a second entry point. It cannot live under `tests/` **at all**
  either: `build-and-test.yml` loops `for p in tests/*/` and runs `dotnet test "$p"`, so a
  `tests/tools/` directory would be treated as a test project and **fail the job**.
- **The provenance line is repo-relative** (`Birko.Framework/tools/…`), not `tools/…`: the generator
  no longer sits beside its output and feeds two suites, so the path a reader types has to work from
  one place.
- **`--check` regenerates to memory and fails on drift**, naming the file. A generated file that has
  drifted from its generator is one somebody hand-edited past the warning at the top.

## Proof

**Regenerated output is byte-identical to what was committed, except the one line that had to change.**
`git diff --numstat` after regeneration:

```
1  1  tests/Birko.Data.SQL.PostgreSQL.Tests/PgColdTableProbeModels.g.cs
1  1  tests/Birko.Data.SQL.SqLite.Tests/ColdTableProbeModels.g.cs
```

Both are the `// GENERATED by …` line. Everything else matches: all 200 and 60 declarations, both
`typeof` lists, the class names, **the blank line after `namespace` that PostgreSQL has and SQLite does
not**, and the `/// <summary>` that SQLite has and PostgreSQL does not. Reproducing those last two
incidental differences is what proves the PostgreSQL profile was reverse-engineered correctly rather
than approximated.

- **`--check` proved able to fail**, not just to pass: hand-editing one type name to `Probe042Tampered`
  reports that file STALE, leaves the other `unchanged`, and exits **1**.
- Both suites build: SQLite **0 errors / 0 warnings**, PostgreSQL **0 errors / 0 warnings**.
- **Zero `.ps1` files remain anywhere in the repository.**

## Acceptance criteria

- [x] The generator runs on Linux — no separator literal in any path expression
- [x] Both generated files are genuinely produced by it, and both headers name the real producer
- [x] Regeneration is byte-identical to the committed files but for the provenance line
- [x] `--check` fails on a hand-edited generated file
- [x] It lives where no `.csproj` globs it and where CI's `tests/*/` loop cannot mistake it for a suite
- [x] Both affected test projects still build
- [x] The `.ps1` is deleted; no `.ps1` remains in the repo

## Out of scope

- **Wiring `--check` into CI.** It would catch a hand-edited generated file on every PR, which is the
  defect this task found, but adding a step to `build-and-test.yml` is a separate decision — the same
  boundary TASK-476 drew around `--fail-on-finding`. **TASK-478 owns it** if wanted.
- **Whether PostgreSQL's 60 is still the right count.** Its header argues the number deliberately
  (*"the question here is whether the CLASS of defect exists at all"*); this task preserved it exactly
  and did not reopen it.
